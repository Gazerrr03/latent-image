## 2. 本地第三章哪些能力应保留

依据当前 `shots.csv`、`quests.csv`、`hotspots.csv`、`evidence.csv`、`links.csv`，而非生成的旧剧本摘要。

当前顺序：醒来得到红光里的画 → 在庄园找艾瑞斯 → 对话/儿歌 → 递线索 → 第一人称调查五张画 → 得到园丁钥匙的提示 → 回客房完成 D3 → 记录 → 睡下。

本地另有五张画的统一检视：`content/visual/inspections.csv`、`inspection_pages.csv`、独立实物/正反面资产。它们包含未跟踪文件，也是本次基准的一部分。

应保留：

1. 最新对白与叙述、递线索的方式及角色认知边界。
2. 五张画的物件身份、现场摆放与笔记本内检视。
3. D3 的推理含义与已有连线候选。
4. 回客房、打字记录、睡眠及跨章节奏。
5. 当前玩家移动、手柄、统一交互目标选择与检视行为。

PR 没有交付第三章的新对白、新证据表、新连线规则、音频或完整迷宫状态机。其运行脚本只有门碰撞补充。

## 3. 接入时必须适配的边界

### 3.1 调试入口与正式入口

PR 的 `C3-T1` 在 `C3-02` 后面，前一行 `next` 为空，因此会按表顺序进入。它自身无文字、无 actions，当前 Director 会等待约 1.5 秒后继续 `C3-03`。这不是独立调试镜头，也没有等待玩家完成迷宫。

另有机位约定差异：节点名为 `cam_hero`，宿主索引时去掉 `cam_` 前缀，因此镜头表通常应填写 `hero`，不是 PR 的 `cam_hero`。该行是 walk 模式，不能据此单独断言玩家实际看到错误机位，但不能作为可靠相机构图接入。

第一阶段建议用 Godot 独立测试场景/探针加载，接真实玩家与宿主，不改正式镜头表。

### 3.2 门

`ded_house.gd` 为 `门入口`、`门出口` 补 StaticBody3D，但本地 `_is_door()` 要求以“门”结尾；仅设置 `door` metadata 不会自动把它加入宿主的 `doors` 索引。

技术方向：优先让新关卡门节点符合已有命名规则，并同步脚本及探针引用。相较为两扇门放宽全局门识别，这样影响范围更小。具体门位、合页与碰撞要实测后再改。

PR 描述称门扇在世界原点；实际 GLB 节点已有非零 translation。因此“门在原点”不能直接当成本机事实。translation 也不能证明门洞对齐，需结合网格顶点、父变换及实际画面核对。

### 3.3 进入与返回

本地 `scene_host.gd` 已有 `_stash_map()` / `_enter_map()`，能保留庄园节点索引和玩家 transform，可作为独立小关卡进入/返回的基础。

但地图保存不等于调查流程保存。正式接入还需要保住：当前调查的待办项、热区、高亮/提示、玩家是否冻结、环境、音乐、对话状态。回廊 `corridor()` 是“等待玩法 done，再继续”的现成参照；不宜直接复制其专属状态或把小屋混进回廊对象。

建议由小屋脚本管理局部规则，Director 等待完成，宿主负责进入/返回，证据仍由现有剧情层发放。先做单关卡的明确接口，暂不建立通用演绎框架。

### 3.4 检视与证据

本地 `_show_hotspot()` 在检视关闭后直接领取热点对应证据，`_inspect()` 随后移除该待办。因此若要让“进入小屋并完成”成为取证条件，必须调整这一处时序；只在画面关闭后切场景会让证据提前到账。

需要同时约定重试、已完成后的再次检视，以及从笔记本打开同一张画时是否可进入。不得让笔记本浏览意外触发场景跳转。

当前 D3 的连线还有其他合法组合。如果要求迷宫成为必经步骤，单纯把 `ev_draw_cloth` 延迟发放仍不足以阻止绕过，必须另审任务完成条件。这是产品选择，尚未批准。

## 4. 尚需选择的章节用途

现行 `docs/02-剧情设计.md` 第三章演绎是“黑布”：从暗房外墙画进入，逐步看到通风口被外侧堵住，指向第四章。PR 则设想进入她的脑海、碰壁三次、从巨眼出口离开；目前两者并不等价。

| 方案 | 玩家体验 | 实现与维护 | 适用条件 |
| --- | --- | --- | --- |
| 仅接资产供独立试玩 | 主线体验暂不变，先判断空间是否成立 | 成本最低；增加候选资源与测试入口 | 尚未接受小屋作为正式第三章玩法 |
| 作为现有演绎的空间改编 | 保留 D3 及黑布调查目标，用小屋承载一次可操作调查 | 中等；需要局部规则、相关线索呈现、进入/返回 | 希望增加玩法，保持当前推理意义 |
| 采用小屋的新体验目标 | 重点转向女孩的记忆、迷宫与碰壁体验 | 较高；需要重定入口、节奏、产出及剧情边界 | 已决定重新设计第三章演绎 |

建议先完成独立试玩包；其后是否改编黑布或采用新玩法，由用户决定。不能把静态拆解视为对任一剧情方向的批准。

## 5. 可分步审查的接入顺序

| 步骤 | 将来改动范围 | 验收条件 |
| --- | --- | --- |
| 1 候选资源包 | A、B、E 与来源记录；独立测试入口 | 来源/SHA 可追溯；Godot 导入、依赖、材质正常；正式 C3 流程无新增跳转 |
| 2 空间可玩 | 只适配小屋场景、门、对应探针 | 用当前真实玩家从 spawn 走到出口；两门按键可操作；碰撞不挡错、不穿、不掉落；代表画面≥45 FPS |
| 3 玩法闭环 | 局部玩法脚本、Director/宿主最小接口 | 按确定规则开始、推进、完成；失败/重复触发可处理；返回原位置并恢复提示和调查状态 |
| 4 正式入口 | 按选定方案修改热点/任务/镜头的必要行 | 在正确时机进入；笔记本不误触发；取证时机与完成条件一致；原有五画检视正常 |
| 5 章节回归 | 玩法文档、关卡文档、验证记录 | 内容校验；两种终局自动通关；第三章真实进入/完成/返回及手柄操作；明确自动通关是否跳过实际迷宫 |

步骤 1、2 可以在章节用途未定前单独开展；步骤 3、4 依赖章节用途、入口和产出已明确。

未来如需新增剧情动作，还需同步 `actions.gd` 白名单、Director 分派和 `docs/06` 动作说明，遵循本地约定。

## 6. 制作材料与诊断工具的缺口

- PR 树中缺 `SundayHouse.blend`、`layout.py`、部分建模脚本、`review/geometry_check.json` 等实际报告。`.blend` 在本地忽略规则内，可能未纳入 Git；缺失不等于作者没有制作，但当前提交不足以供另一台机器重建与复核。
- `02_plan_drawing.py` 依赖 Windows 字体路径，`08_make_level.py` 写死 `D:\github\acknowledged`，不能在 macOS 原样运行。
- `08_make_level.py` 输出内容与提交的最终场景不一致：生成器没有最终场景中的 doors.glb 和门脚本接线。重跑会丢失这些后续改动，不能用它覆盖最终场景。
- `06_export_glb.py` 描述的是压平成代表色，提交的 GLB 实际包含烘焙图像；当前脚本不足以说明最终烘焙交付的完整生成过程。
- `doorcheck.gd` 直接转门测碰撞，绕开真实宿主的开门识别，不能发现命名未登记的问题。
- `doorpos.gd` 把局部 `get_aabb()` 输出标为 worldAABB，未乘 global_transform，不能据其输出认定门的世界位置。
- `probe_shot.gd` 自建环境和相机，可作资产观察，但不能替代真实游戏滤镜、环境与帧率验证。
- 无关的两张庄园法线导入改动应排除；其中 floorboards 的压缩、法线识别和 mipmap 参数均被改变，超出小屋补丁范围。
