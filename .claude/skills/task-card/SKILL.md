# 任务卡生成

用户是项目负责人，队友不懂游戏开发，可能能力有限。你的工作是把用户的一句粗略需求，变成队友拿到就能开工、做完能被逐条验收的任务卡。

## 步骤

1. **读上下文**（只读与需求相关的部分）：
   - `docs/任务/README.md`：已有编号与任务，避免重复，取下一个可用编号。
   - `docs/任务/_模板.md`：必须使用的格式。
   - 按需求类型读：3D → `docs/03-空间与关卡设计.md`、`docs/09-团队协作与任务派发.md` 第 5 节命名约定；2D/UI → `docs/04-美术与声音风格.md`；文本 → `docs/02-剧情设计.md`、`docs/05-AI叙述代理与文本规范.md`、`docs/06-技术方案.md` 第 2 节；声音 → `docs/04` 第 7 节。
   - 剧情细节以 `docs/归档/故事分支分镜（MVP 预设分支）.pdf` 为准，引用时写出镜号。

2. **补全用户没说的部分**，用设计文档里已有的信息，不要编造新的剧情事实。真正无法确定、会影响交付的点（例如截止日期、负责人）留空并在最后向用户提问。

3. **写任务卡**，存为 `docs/任务/T-<编号>-<简短中文名>.md`，严格按模板。质量要求：
   - “为什么做”说清楚玩家在哪里、怎么看到它，链接到文档章节和分镜镜号。
   - 交付物写到文件名、格式、尺寸、存放路径。3D 物体名遵守 `hs_` / `spawn` / `exit` / `-col` / `guide_` 约定。
   - 规格尽量用数字；必须出现的元素逐条列出。
   - 验收清单每条都能直接判断“是 / 否”，不要写“效果好”这类主观条目。
   - “不需要做”主动排除程序会负责的部分（灯光烘焙、渗漏变体、文字排版等），防止队友过度投入。
   - 设一个 24 小时内的草稿检查点。
   - “兜底”写明队友没交付时，用户 + agent 用什么替代（灰盒、CC0 素材、Codex 生成、从分镜提取）。
   - 用非技术语言；术语第一次出现时用一句话解释。

4. **更新总表** `docs/任务/README.md`：新增或更新这一行，状态为“待领取”。

5. **回复用户**：给出任务卡链接、一句话概要，以及需要用户确认的 1—3 个问题（如有）。不要在回复中重复整张任务卡。

## 拆分规则

- 一张卡只给一个人，一个交付主题。需求太大时（如“把所有房间都做了”），拆成多张卡，并说明拆分理由。
- 程序任务（Godot 工程、脚本、管线）不写成任务卡，那是用户和 agent 自己的工作。
